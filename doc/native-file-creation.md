# Native file creation — verified component

The native coding implementation includes `create_file` alongside `edit_file` when the trusted server is configured with `--workspace-edits approved`. Each operation requires its own controller decision. Source `e93f28c7e6d7c214f1c0d5e049ad9408128b4ad5` compiled in Release and passed all **31 native and 30 extension contracts** in [isolated CI run 37621404384](https://github.com/xlang-foundation/xMind/actions/runs/37621404384): [complete CTest output](evidence/native-file-creation-ci-ctest.log), [source/runtime provenance](evidence/native-file-creation-ci-provenance.json). The runtime is native xlang3 with the reviewed SQLite prerequisite; no CPython process or bridge is used. Local compilation remains deferred during the independent xlang3 full timing suite; its deferral is not evidence of a local pass.

The model supplies only relative path and UTF-8 content. Planning opens the workspace and existing parent directories, rejects traversal/device/ambiguous names and directory reparses, verifies absence of the final entry, and captures workspace/parent identity and content/hash. It does not create parent directories or the file. The durable proposal records absence, the exact destination/content and parent identity. Models/views cannot supply a grant, parent identity or successful outcome.

After the exact single-use claim, the backend reopens and verifies the parent chain, then calls Windows `NtCreateFile` with a single filename relative to the retained parent handle and `FILE_CREATE`. Existing entries fail rather than opening or overwriting them. Parent handles deny write/delete sharing during the effect. The file receives bounded writes, flush and readback through its own exclusive handle. Empty content still creates an actual file. Creation is an effect before the first content write: interruption after successful creation leaves uncertainty, including an empty/partial file. There is no automatic cleanup or replay. The native API's directory-relative and create-new semantics are documented by [Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile).

The native executor uses the existing embedded-xlang3 operation journal and workspace resource ownership. Parent/absence conflicts before creation record failure. Unknown creation or post-creation failure records uncertainty. Failure to preserve a claimed outcome stops admission for recovery. Restart must quarantine executing claims without deleting or replaying their filesystem effects. Automatic creation reconciliation is not implemented; the existing uncertain-edit inspector applies only to recorded replacements.

The passed native component contract exercises actual approved/empty/Unicode creation, existing-name preservation, parent replacement, denied/cancelled approval, real junction rejection and a real storage fault after file creation followed by restart. The model/HTTP/CLI contract verifies creation, denial, stale-name conflict, cancellation while awaiting approval, result continuation and pending-approval restart with labeled synthetic inference. Extension contracts verify new-file review and absent-to-proposed comparison using labeled fixtures. The actual interactive preview now uses this isolated tested bundle, remains unseeded and has no model configured. Populated editor creation, live-model/coding-task completion, process/shell tools and attributed creation reconciliation remain incomplete. Process death during a partial write and cancellation after physical creation are not established by these tests.
