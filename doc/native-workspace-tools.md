# Native workspace tools

The C++ Windows workspace implementation provides actual file reading, one-directory listing and literal text search, plus typed model tool definitions and exact argument-shape validation. The native agent loop invokes these tools and persists their actual results. The filesystem adapter has no model response generator or simulated effect; HTTP execution stays in the separate server adapter.

The root is an opened directory handle. File handles are opened, checked against the root's normalized path and then read. Strict normalized path casing avoids treating a case-distinct sibling as the authorized root. Caller paths must be relative; absolute paths, parent traversal, stream/drive syntax and embedded NUL are rejected. Windows extended paths use native separators. Hard-linked files are denied pending a separate explicit alias policy.

Directory listing operates on the verified handle using [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex) and [FILE_ID_BOTH_DIR_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_both_dir_info), rather than validating a directory and reopening a pathname for enumeration. Directory reparse points are not traversed. Reads verify the final file target, so an outside-workspace junction target is denied. Returned entry metadata includes link/directory/file kinds.

Read limits are 1 MiB per UTF-8 text file; binary/NUL-containing or invalid UTF-8 files are rejected. Listings return up to 1000 entries with `truncated`. Search skips `.git`, `.venv`, `.agentflow`, `node_modules` and `__pycache__`, follows no listed links and reports skipped entries. Search bounds are 10000 inspected entries, 64 MiB of file content and 100 matches. Each preview is at most 4096 UTF-8 bytes and carries `text_truncated`. Directory and total search truncation remain explicit; absence of a match in a truncated search is not a complete negative result. Cancellation is checked between directory/file/read/line operations.

## Verified scope

The native tools contract passed against independently created real filesystem fixtures: nested UTF-8 and normal Windows case lookup, literal path/line matches, Unicode preview clipping, argument validation, cancellation, concurrent reads, oversized/binary rejection, outside-root junctions (including a nested target), hard links, excluded directories and truncation. Junction creation failure fails the test rather than skipping boundary checks. The outside marker remains unchanged. No real or synthetic model was invoked by this filesystem test.

The first full run exposed a nested-path separator issue; the corrected implementation passed the targeted tools contract. The other ten native contracts passed during that full run. Current tools evidence: [native-workspace-tools-ctest.log](evidence/native-workspace-tools-ctest.log).

The [native agent loop](native-agent-loop.md) now invokes these read tools and forwards their actual results to the provider. Writes, patch review/recovery, shell/PTY, Git, diagnostics, ignore-file semantics beyond the listed exclusions, paginated listings, other OS implementations and complete tool permissions/approvals remain required. The read-only library does not establish a complete coding agent or OpenCode parity.

## Edit implementation gate

`identity()` uses the opened root's volume/file identifiers from [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info). It rejects unavailable/zero file identifiers and a changed root path on an existing runtime. Unlike a path-only identity, reopening the same directory object after a move retains its local policy identity on the tested filesystem. Alias, distinct-directory and directory-move/reopen tests passed. This identity is local to one computer/filesystem; shared servers must namespace it by authenticated worker identity, and unsupported filesystem semantics require a separate adapter. The native operation journal and permission waiter also passed their component contracts; they do not yet expose a write tool.

`snapshot_file()` captures the bounded UTF-8 contents, file identity, workspace identity and SHA-256 from one verified open file handle. Normal reads keep their existing output contract. Passing snapshot tests independently compute the fixture hash using Node.js and modify the actual file in place to distinguish stable object identity from changed content. The snapshot is backend-only and grants no permission. It captures preconditions, not a filesystem transaction or a completed file edit.

`plan_replacement()` builds a literal edit proposal from that actual snapshot. The caller declares the expected non-overlapping occurrence count; missing/ambiguous matches, invalid UTF-8/NUL text, unchanged replacement and oversized output are rejected. The result carries the original snapshot plus proposed after-content/hash while leaving the file untouched. Tests passed for exact proposed bytes, independently computed hashes, rejected proposals and unchanged actual files. This planner is not offered as an executed coding tool; controller authorization, precondition revalidation, actual application and recovery must be implemented and verified before a write tool is exposed. Evidence: [native-permission-planning-ctest.log](evidence/native-permission-planning-ctest.log).

Microsoft documents a directory-relative target for [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), used with [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). The documented extended rename [POSIX flag](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) permits replacement despite open handles and leaves those handles attached to the replaced file. This means an open handle alone must not be claimed as a conditional file replacement guarantee. These APIs are candidates for the Windows edit adapter; their actual behavior in the chosen implementation remains untested.

`apply_plan()` is a backend-only Windows in-place effect primitive. It validates both hashes, workspace identity, file identity and actual prior bytes before writing through an exclusive read/write handle. It rejects final reparse points and hard links, preserves file identity, truncates the old tail, flushes and verifies actual bytes afterward. Any error or cancellation after a write/truncation attempt raises `ToolMutationUncertain`; callers must retain uncertainty rather than retry. `fingerprint_file()` inspects bounded raw bytes for later reconciliation, including invalid UTF-8 from interrupted writes, without returning them to the model.

The real disk contract covers Unicode/longer, shorter and empty replacements, changed content, a different actual file object with identical bytes, wrong identity/hash/workspace, traversal, outside junctions, hard links, pre-write cancellation and an actual competing read handle. Independent Node reads/hashes check the resulting empty file and raw binary fingerprint. Evidence is recorded in [native-file-application-ctest.log](evidence/native-file-application-ctest.log).

`EditExecutor` connects this primitive to `PermissionWaiter` and the operation journal. Its owned plan is serialized into an exact durable proposal with actual before/after contents, file identity and hashes. The repository bounds this payload; oversized/escaped proposals fail before an effect. The adapter awaits an attributed decision and a single-use claim, then applies that same owned plan and journals the actual result. Known pre-effect failures record failed; possible partial effects record uncertain. If outcome persistence fails, `EditOutcomeUnrecorded` requires stopping execution and recovery; the adapter preserves the executing claim and never retries the file effect. Successful application followed by an outcome storage fault is tested with a fixture-only SQLite trigger through embedded xlang3: actual bytes change, the success transaction rolls back, and reopening quarantines the claimed operation as uncertain.

The executor contract also covers denied/pending/cancelled proposals without effects, approved stale edits, exact persisted review content, actual approved changes, duplicate rejection, controller attribution and durable reopen without replay. Evidence: [native-approved-edit-ctest.log](evidence/native-approved-edit-ctest.log). No model or public approval route is involved in this component test. Approval API/controller authorization, agent/tool integration, partial-write/process-kill tests and uncertainty reconciliation remain required before enabling agent writes. Recovery retains recorded before/after bytes, but automatic restore/reconciliation is not implemented.

Application is in-place, not atomic replacement; an exclusive ordinary file handle does not establish protection against every external writer, mapped view or filesystem replacement mechanism. The journal serializes backend effects only. Recovery must inspect actual file state and retain uncertainty until it can prove the outcome. Model definitions and public routes still expose no writes.
