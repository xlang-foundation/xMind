The current official revision is `2026-07-28`. It carries protocol version and client capabilities on every request, with discovery instead of the earlier initialization handshake. The client must support this revision and interoperate with legacy `2025-11-25`; implementing only the old handshake would miss current servers. A modern unsupported-version response identifies a modern server and must not trigger an initialization fallback. See [official versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [stdio negotiation](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), and [discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).

Requests carry `params._meta` with `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`; client identity is supplied for display, never used as authorization. Modern results distinguish completion from additional input requests. Legacy missing result types retain their documented completion interpretation. Server-initiated requests belong only to the legacy era. The native implementation must distinguish malformed wire data, peer RPC errors, tool errors and incomplete input interactions. It must not flatten all of them into successful text. See [base protocol and metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/index).

The implementation proceeds through these product components:

1. A transport-neutral bounded UTF-8/JSON-RPC codec and request correlation layer. Reject duplicate fields, excessive nesting, malformed IDs, batches and unframed stdout logging. Bound messages, pending requests and unsolicited notifications; preserve request/result identity through fragmented reads.
2. Backend-owned stdio processes and Streamable HTTP adapters. Process launch comes from trusted server configuration, with explicit executable/arguments/environment and scoped encrypted credentials. Never inherit the complete backend environment into a plugin process. Use native process ownership, restricted handle inheritance and bounded stderr draining. Close stdin for graceful shutdown; terminate only the owned process group after its deadline. HTTP authentication and OAuth belong in the access adapter, separate from protocol/core logic.
3. Modern discovery/version selection and legacy initialization fallback, with capability validation and cancellation. Process death retires in-flight work. Discovery/listing may be repeated, but an effectful call is never automatically replayed merely because its response was lost; its durable operation remains uncertain.
4. Paginated tools/resources/prompts and schema validation, preserving structured content and unsupported content boundaries. Namespace tools by trusted configuration identity. Treat server instructions, annotations and result content as untrusted data. Remote `readOnlyHint` is not an authorization grant. See [official tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).
5. Exact operation proposal/approval/claim/outcome integration for remote calls, then agent registry and CLI/VS Code configuration/inspection. The journal binds server configuration revision, selected tool and exact arguments to the authenticated controller. Runtime cancellation or transport loss after dispatch cannot prove that the server performed no effect. Recovery and attributed resolution remain explicit work.

Independent Node peers will exercise real native pipes and HTTP messages, both protocol eras, fragmented UTF-8, unsupported-version negotiation, pagination, structured/tool-error results, cancellation, stalled/terminated peers and denied calls without dispatch. SDK interoperability is an additional gate, not a substitute for these protocol and effect contracts. Modern additional-input requests, subscriptions, OAuth, resources/prompts and full tool integration stay on the delivery list even if the first codec/process contracts pass. Full MCP, A2A and graph support are not delivered by a wire parser alone.

Windows stdio implementation constraints: launch the explicitly configured executable directly, suspended, assign the owned job before resuming it, and supply only stdin/stdout/stderr via `STARTUPINFOEX`'s handle list. Construct an explicit environment; backend access/provider credentials are not inherited wholesale. A job controls lifetime of descendants, not their filesystem/network authorization. See Microsoft's [redirected child I/O](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output), [handle-list attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and [job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Use cancellable overlapped parent pipe I/O rather than an unbounded blocking write to a peer that may stop reading. Drain stdout and stderr independently into bounded transport state; feed the wire codec on its single owning thread. Discard raw stderr by default so a plugin cannot expose credentials through backend/UI diagnostics. Cancellation must wait for I/O completion before freeing its buffer or `OVERLAPPED` state; a cancellation request alone does not prove completion. See Microsoft's [pending I/O cancellation rules](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations). Graceful shutdown closes stdin, waits to a deadline, then terminates only the owned job and joins the I/O workers. Process/pipe tests must verify EOF, stalled readers, output backpressure, cancellation, descendant cleanup and absent inherited backend secrets before connecting this adapter to a model tool.

## Shared effect resources and bounded native schema evaluation

Subsequent source extends repository schema to version four. An operation retains its verified workspace plus additional backend-owned effect-resource keys. Claims check every resource within the same SQLite `BEGIN IMMEDIATE` transaction; no partial multi-resource claim is possible. MCP always adds the stable `mcp-server:<configuration-id>` resource, independent of configuration revision or workspace. Executing calls serialize other callers to that configured server, and uncertainty blocks them across workspaces. Resource states/events change atomically with the operation. Version-three MCP payloads are migrated into stable server resources; unattributable legacy MCP records fail migration. Failed migrations roll back. Configuration aliases representing the same external account still need explicit account-resource mapping; server identity alone does not establish account-wide isolation.

MCP schema admission and input/output validation now run through the adjacent native `xmind_schema_worker.exe`, not inside the agent process. A fresh owned worker receives only bounded schema/argument JSON strings via private JSON-RPC IPC. It uses the pinned native 2020-12 validator with no network/file resolver. The process gets 128 MiB committed-memory, two seconds user CPU, one process and a two-second wall deadline; cancellation retires the owned job. These are resource/lifetime limits, not filesystem/network sandbox claims. Worker failures are distinguished from actual schema/argument rejection. Received peer acknowledgements finish output validation and journaling within a fresh bounded worker budget even if the run was cancelled. The worker is included in native development bundles and carries no CPython execution/bridge.

The full twenty-six-contract local run passed. Existing real MCP file-effect fixtures now cover stable server quarantine across different opened workspaces. Repository fixtures cover multi-resource contention, independent domains, immutable resource binding, revision changes, migration/backfill and rollback. The new independent native budget fixture queries actual Windows job limits, observes committed-memory allocation refusal, and deliberately stalls a child to test wall timeout/cancellation; it never supplies production schema validation. Actual production-worker fixtures separately validate schemas/arguments, reject unavailable references and test expensive regex rejection/containment plus subsequent healthy evaluation. CPU flags are queried; exact OS CPU-timer scheduling and full upstream schema conformance are not claimed. Persistent MCP configuration, model/CLI/view activation, SDK interoperability, account-scope mapping and other protocol features remain incomplete.

The native agent now loads durable backend-owned stdio configuration, starts an owned MCP client for each enabled server per run, discovers and validates its actual tools, and adds their bound aliases to the model request. Configuration is replaced only by trusted startup or an offline administrator while the backend is stopped. The xlang3 information repository stores it separately from encrypted credential blobs. This is an immutable service snapshot, not dynamic/team configuration administration. Absolute executable and working-directory paths are required. Arguments are public literal metadata; use credential references for secrets.

Example configuration file (replace paths with the actual trusted server):

```json
{"servers":[{"id":"project-tools","transport":"stdio","enabled":true,"executable":"D:\\tools\\server.exe","working_directory":"D:\\project","arguments":[],"credentials":[{"name":"SERVICE_API_KEY","scope":"server","id":"project-tools-key"}]}]}
```

Import and provision through the compiled native administrator while xMind Server is stopped:

```powershell
.\build\native\Release\xmind_admin.exe --db STATE_DB --modules XLANG3_MODULES --stdlib PURE_STDLIB import-mcp CONFIG_FILE
.\build\native\Release\xmind_admin.exe --db STATE_DB --modules XLANG3_MODULES --stdlib PURE_STDLIB put-mcp-credential project-tools SERVICE_API_KEY PRIVATE_SOURCE_ENV
```

`PRIVATE_SOURCE_ENV` names an environment variable privately provisioned in the administrator process. The secret itself is never a command argument or printed output. The administrator derives scope/ID from the registered reference and purpose from the exact configured command, directory, server ID and normalized environment name. Command changes require a credential provisioned for the new purpose. Existing credential IDs cannot silently change purpose; assign a new reference when changing the command. Storage uses the existing user-bound Windows DPAPI protection and embedded xlang3 SQLite adapter. There is no CPython executable/bridge.

The native server also accepts `--mcp-config CONFIG_FILE` before creating workers; omitting it restores saved settings. Enabled MCP execution requires the trusted execution workspace and explicit supported model-tool capability. A model-free server can list saved metadata without executing tools. Authenticated `GET /v1/mcp/servers` and `xmind_cli PORT mcp-servers` expose only ID, revision, enabled flag and transport, with `runtime_state:"per_run"`; they do not expose command paths, arguments or credential references/values. An uncertain MCP operation offers no retry or file-inspection inference; a succeeded operation is labeled peer-acknowledged, without independent verification.
