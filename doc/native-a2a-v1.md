# Native A2A 1.0 core operations

The C++ adapter now implements the A2A 1.0 JSON-RPC wire for `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask` and `SubscribeToTask`. It shares the native executor, retry mappings and xlang3 persistence with the existing v0.3 interface. The protocol reference is the [A2A specification](https://a2a-protocol.org/latest/specification/), audited on 2026-10-07; the independent official SDK peer remains pinned at **1.3.0**. No JavaScript SDK is part of the production core.

Send `A2A-Version: 1.0` to `/a2a` and to `/.well-known/agent-card.json`. Missing/empty version headers select v0.3; `0.3` explicitly selects the same legacy wire. Other versions fail before admission. The version-1 card exposes JSON-RPC interfaces for both versions with bearer security and the actual executable skills. A version-1 request uses its own operation names, enum strings, text parts and response envelopes, rather than accepting the legacy wire under a newer label.

```json
{"jsonrpc":"2.0","id":"request-1","method":"SendMessage","params":{"message":{"messageId":"client-message-1","role":"ROLE_USER","parts":[{"text":"Explain this repository"}]},"configuration":{"returnImmediately":true,"historyLength":8}}}
```

Without `returnImmediately: true`, a version-1 send waits for an actual terminal or interrupted state and returns the latest Task and artifacts. Legacy `blocking: true` now uses the same waiting path. Blocking waits and streams share two reserved interaction slots in the local four-worker HTTP adapter; inspection, listing and cancellation remain available. Viewer disconnects release the waiting interaction without cancelling its task. Streaming configuration does not turn a stream into a blocking JSON response. Version-1 subscription rejects terminal tasks; completed v0.3 resubscription remains available under its existing contract.

`ListTasks` lists authenticated local-owner root runs, excluding internal graph children. It supports context/state filters, page sizes 1–100 (default 50), history bounds, timestamp cutoffs and optional artifacts. Artifacts are omitted by default. Opaque cursor tokens carry a status position, journal watermark and filter binding; there is no offset pagination. Tokens are not credentials or cryptographic authorization: every page still passes the owner-token boundary and its filters. They remain usable after a server restart. Pages reflect live records: tasks updated beyond a page sequence's watermark belong to a fresh listing, and totals can change with subsequent status updates. This is not a materialized historical snapshot.

Schema version 9 stores measured UTC status-update times and their journal sequences in the same transaction as the lifecycle event. Known-time tasks sort by time descending, then by sequence for ties. Earlier journals did not record wall-clock times: migration preserves those tasks without inventing dates, places them after timed entries in actual journal order, and rejects timestamp-filtered queries when matching legacy entries have unknown times. A later real status transition gives that task a known time. Legacy ordering is a compatibility behavior, not proof of full timestamp semantics for old records. SQL I/O remains through embedded xlang3.

Both wires normalize their supported text messages into the same durable retry identity. A completed request can be retried across versions without reexecution, even when the reopened server has no configured agent. Reusing its ID with changed text or context still conflicts. Existing task-history attribution and legacy-history safeguards remain in place.

Inbound history now projects the original admitted text parts, including empty text parts, each part's metadata and message metadata, from the durable incoming-message identity. The model still receives the combined text prompt; protocol metadata is not added to that prompt. Projection matches the task's mapped input message ID and does not copy metadata to other runs in the same context. Both version wires, blocking sends, task reads, listings and completed retries use this projection. Existing schema-8/9 inbound identities already contain these details, so no migration or fabricated historical backfill is needed. Media-type defaults remain normalized, request-level RPC metadata is not returned as message metadata, and messages originating outside A2A retain their ordinary generated text projection.

The history-fidelity regression exercises actual native admission and storage with explicitly synthetic provider replies. Raw v1 and v0.3 histories preserve nested message/part metadata, empty parts and their order; the official SDK decodes the resulting multipart history. Checks cover blocking responses, listing, completed streaming replay, changed-metadata retry conflicts, separation from a subsequent run in the same context, and reopening without an available executor. The first full run passed the new v1 check but failed an older assertion expecting flattened history. That assertion now requires the original parts and separately verifies the provider's combined prompt; the original failure is retained in [initial build output](evidence/native-a2a-history-initial-build.log).

Final history-fidelity validation passed **50/50 native and 60/60 extension contracts**, with no skips. `native_a2a_v1_http_contract` uses the official SDK with no compatibility resolver or transport enabled, and asserts actual version-1 wire headers/methods. It verifies default blocking, legacy blocking, capacity before admission, real control availability, disconnect isolation, streams/subscriptions, cancellation, failure reporting, scoped listing, pagination, measured times, malformed/version rejection, cross-version retries and restart. Provider replies are explicitly synthetic fixtures. `native_task_list_repository_contract` tests clock transaction faults, root-only visibility, cursor watermarks and schema-8 migration; its explicit lifecycle writes are synthetic storage fixtures.

The first full run rejected the listing fixture because an omitted SDK enum default serialized as `UNRECOGNIZED`. The adapter correctly rejected that request. The fixture now constructs a valid SDK request with `TASK_STATE_UNSPECIFIED`; no SDK, platform or production behavior was patched to hide the rejection. Final verification passed **50/50 native contracts** and **60/60 extension contracts**, with no skips. Full compliance remains unproven. Task continuation/referenced tasks, file/data parts, push notifications, extended cards, remote delegation, additional bindings, tenant/team policies and broader product parity remain required. Nonempty tenant routing is explicitly rejected in this local-owner adapter. Its runtime does not yet model separate rejected/auth-required lifecycle states. Broader content/media-type interoperability and legacy timestamp behavior still need coverage.
