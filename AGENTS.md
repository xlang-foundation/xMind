# xMind development constraints

- Product architecture revision (2026-10-09): preserve three explicit components, **Agent Runtime / AgentFlow + Coding Agent / Harness + AI Model Gateway**. Old xMind, OpenCode and LiteLLM are capability/behavior references; implement the platform natively. Coding uses the general runtime and shared tools. The gateway owns provider adapters, model discovery/capabilities, credentials, streaming and actual usage.
- The primary product executable is `xmind`: `serve` owns persistent execution; the console is a client. Consolidate internal native entry points into modes too. Existing launchers/manifests are transitional until actual installed package/owner migration is verified; do not claim a build target alone completed that migration. Automatic console profile discovery/start remains required. Closing a client detaches observation rather than cancelling runs.
- Public authoring concepts are **Agent + Tool + Graph / Super-agent + Skill**. Do not introduce separate Action or Func entity types. A tool may be selected by an agent or scheduled as a graph node; use one registry and the same schemas/permissions/receipts. Ordinary inline functions remain implementation code; MCP is a connector to tools. Preserve file-patch `action` fields as operation semantics, not AgentFlow entity types.
- Support YAML + Markdown with optional xlang3 Python implementations and Python programming APIs that register the same validated native definitions. Planning is optional; the coding default is the model/tool loop. Graph readiness determines eligible work; scheduling determines when/where it executes. No token-saving claim without actual whole-task usage and outcome comparison.
- Target configurable in-process and agent-worker execution using xlang3 shared-memory IPC for local native transports, while HTTP commands/SSE serve browser and VS Code. Worker placement, IPC integration and shared UI SSE are not completed by the current SDK smoke/dispatcher checks. Runtime-owned persistence, approvals and effect reconciliation remain mandatory; a worker process/IPC alone is not an OS sandbox. See doc/runtime-product-design.md and doc/native-ipc-worker-design.md.

- The VS Code extension must use a dedicated right-hand secondary sidebar like Cursor/Copilot/Codex, with native WebviewView contributions. Keep Explorer on the left. Put the composer and backend model chooser at the bottom, render conversation history and Markdown/code properly, and show actual per-response provider token usage. Do not invent metrics or place the main agent UI in a center editor webview tab. Keep platform logic in the C++ backend and access/authentication in the thin extension host.

- Every product change must implement the final architecture. Do not simulate agent/model/tool execution or expose manual state changes as a working agent. Keep synthetic fixtures in tests/demos and label their scope. Product run lifecycle belongs to the real execution engine; unsupported features remain explicitly incomplete. Report only behavior directly verified at the claimed scope.

- Scope revision (2026-10-07): xMind OSS includes the local C++/xlang3 agent and coding backend, SQLite persistence, single/graph agents, broad native provider support, MCP/A2A, CLI, browser UI and the VS Code extension. Team-server features, PostgreSQL, WebRTC/signaling and the standalone Electron IDE are excluded from OSS delivery and reserved for CantorAI's closed-source Nexus project in the sibling Nexus folder. Earlier proposals are not remaining OSS requirements. Do not implement, package or count private features toward OSS completion.
- xMind OSS uses SQLite behind C++ repository contracts, with database I/O through embedded xlang3. Keep migrations, transactions and run ownership rules in the backend. Follow doc/architecture.md for current OSS scope.
- Connection profile revision: xMind must support a Local profile and Nexus server profiles over the same versioned command/event protocol. Local mode uses the local C++/xlang3 runtime and SQLite. A Nexus profile binds that local agent/workspace to the private server's authenticated team coordination and distributed execution capabilities. The generic profile/client/worker protocol belongs in OSS; Nexus implements shared PostgreSQL, team authorization, scheduling and later Cantor Cluster integration. Do not confuse connection profiles with model-provider profiles, silently fall back between profiles, or access Nexus PostgreSQL directly from clients.

- Isolate the agent/coding runtime from UI views. OSS clients use the local backend's command/event contracts; UI adapters do not own execution, permissions or persistence. This separation remains required without WebRTC or Electron implementation.
- Coding must support the native console CLI, browser UI and VS Code extension. Preserve existing CantorAI/WorkSense installations; Electron reuse belongs to the separate closed-source product.
- xMind Server remains the local backend/API name in OSS. SQLite is owned by that backend and accessed through xlang3, never mounted by clients. Local-owner authentication and tool-effect authorization remain required. Optional Nexus binding is an OSS connection/agent capability; the team-server implementation remains private.
- SQLite operations must go through embedded xlang3, including secret and general information storage. C++ owns repository contracts and encryption but calls xlang3 for database I/O. Do not link the direct-SQLite reference as production persistence. Store encrypted credential blobs separately from public metadata; do not expose plaintext secrets to clients or model context.
- The user's latest architecture requirement is native C++ implementation of the platform. OpenCode and LiteLLM are behavior/capability references only; do not execute, embed, copy their implementations or add their SDKs as the core platform. C++ owns backend services, sessions, agent/model/tool orchestration, graphs, permissions, protocols, persistence and provider adapters. The earlier Python/FastAPI agent prototype was removed. Do not reintroduce it as the platform or as evidence of native completion.
- The user confirmed C++ owns the core, with embedded xlang3 for scripts, skills and pure-Python libraries, then authorized continued work after the architecture was drawn. Follow doc/architecture.svg and doc/architecture.md. Use xlang3's supported embedding/native SDK; never retain the old xlang package ABI merely by changing include paths. VS Code's required JavaScript/TypeScript host adapter should remain thin; all platform logic belongs in C++.
- Execute Python application code, tests, probes and Python tooling with the sibling xlang3 runtime. The user explicitly prohibited CPython use. Do not fall back to CPython when xlang3 compatibility fails.
- Use Node.js for the VS Code extension and independent TypeScript MCP peers.
- Record and fix xlang3 compatibility gaps or continue independent work. Do not conceal a gap by changing the Python interpreter or monkey-patching platform identity.
- CPython-compatible pure-Python standard-library and third-party source packages are explicitly allowed under xlang3. Native dependencies must use xlang3-compatible bindings; do not rely on CPython native extension binaries. Library reuse is not authorization to execute the CPython interpreter.
- Install pure-Python packages from PyPI using pip executed by xlang3. If a pure-Python package exposes a missing native runtime capability, discuss the exact gap and proposed resolution with the user before changing native code or selecting a workaround. Continue independent authorized work meanwhile.
- AgentFlow's repository-local commit email is shawn@cantorai.com. Preserve global Git settings and sibling repository identity.
- Preserve the upstream history and applicable license notices. Full OpenCode parity, MCP/A2A, graph execution and editor validation remain required by the active project goal.
