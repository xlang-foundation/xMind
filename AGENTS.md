# xMind development constraints

- The VS Code extension must use a dedicated right-hand secondary sidebar like Cursor/Copilot/Codex, with native WebviewView contributions. Keep Explorer on the left. Put the composer and backend model chooser at the bottom, render conversation history and Markdown/code properly, and show actual per-response provider token usage. Do not invent metrics or place the main agent UI in a center editor webview tab. Keep platform logic in the C++ backend and access/authentication in the thin extension host.

- Every product change must implement the final architecture. Do not simulate agent/model/tool execution or expose manual state changes as a working agent. Keep synthetic fixtures in tests/demos and label their scope. Product run lifecycle belongs to the real execution engine; unsupported features remain explicitly incomplete. Report only behavior directly verified at the claimed scope.

- xMind Server supports SQLite or PostgreSQL behind a common C++ domain repository contract, with database I/O through embedded xlang3. Keep SQL dialect, schema migrations and concurrency/ownership rules in backend adapters. PostgreSQL is planned, not verified. Follow doc/database-backends.md.

- WebRTC topology: Live Backend ↔ WebRTC ↔ Client View; xMind Server exchanges authenticated signaling. View clients include HTML/browser, Electron and later mobile. Keep signaling and data paths distinct; backend-side RTC adapters remain outside the core. See doc/webrtc-views.svg.
- Isolate the agent/coding runtime from UI views. A runtime on Node A must support viewers elsewhere. WebRTC/Electron dependencies belong to access/view adapters outside the core; use transport-neutral command/event contracts. Follow doc/runtime-view-separation.md and its SVG.
- Coding must support console CLI, a standalone Electron IDE and editor plugins (VS Code first). The user authorized reusing/copying the existing CantorAI/WorkSense Electron runtime on this PC. Inspect the actual runtime and applicable instructions before reuse; preserve the installed WorkSense application and do not assume its packaged executable is a development Electron launcher. Desktop orchestration stays in the C++ backend.
- Support local and company/team deployment through the same xMind Server core/API. SQLite remains owned by the selected server and accessed through xlang3, not mounted by clients. Follow doc/server-deployment.md and doc/deployment.svg; team authentication, authorization and scoped workspace workers are required before claiming shared-server readiness.
- SQLite operations must go through embedded xlang3, including secret and general information storage. C++ owns repository contracts and encryption but calls xlang3 for database I/O. Do not link the direct-SQLite reference as production persistence. Store encrypted credential blobs separately from public metadata; do not expose plaintext secrets to clients or model context.
- The user's latest architecture requirement is native C++ implementation of the platform. OpenCode and LiteLLM are behavior/capability references only; do not execute, embed, copy their implementations or add their SDKs as the core platform. C++ owns backend services, sessions, agent/model/tool orchestration, graphs, permissions, protocols, persistence and provider adapters. The Python/FastAPI code is a historical prototype, not the target implementation or evidence of native completion.
- The user confirmed C++ owns the core, with embedded xlang3 for scripts, skills and pure-Python libraries, then authorized continued work after the architecture was drawn. Follow doc/architecture.svg and doc/architecture.md. Use xlang3's supported embedding/native SDK; never retain the old xlang package ABI merely by changing include paths. VS Code's required JavaScript/TypeScript host adapter should remain thin; all platform logic belongs in C++.
- Execute Python application code, tests, probes and Python tooling with the sibling xlang3 runtime. The user explicitly prohibited CPython use. Do not fall back to CPython when xlang3 compatibility fails.
- Use Node.js for the VS Code extension and independent TypeScript MCP peers.
- Record and fix xlang3 compatibility gaps or continue independent work. Do not conceal a gap by changing the Python interpreter or monkey-patching platform identity.
- CPython-compatible pure-Python standard-library and third-party source packages are explicitly allowed under xlang3. Native dependencies must use xlang3-compatible bindings; do not rely on CPython native extension binaries. Library reuse is not authorization to execute the CPython interpreter.
- Install pure-Python packages from PyPI using pip executed by xlang3. If a pure-Python package exposes a missing native runtime capability, discuss the exact gap and proposed resolution with the user before changing native code or selecting a workaround. Continue independent authorized work meanwhile.
